# Canary v1 formats

**Frozen for v1 on 2026-09-30. Changes need a version bump.**

Amended the same evening, before any program wrote these formats, so no version changed.
The amendments add the `hash_without_policy` warning, split the declared-payment reason in
two, and record how the dashboard's status line differs from the terminal's.

**Revised 2026-10-01.** Three rules in `canary check` changed. None changes a format, so
no version changed. The state file is still `canary-state/1`, the evidence file is still
`canary-evidence/1`, and no field, state or reason code was added.

- **A server with one verified record can no longer stop the run.** Before, any answer
  outside the v1 API stopped `canary check` with exit code 5, and the run saved nothing.
  A withholding server could answer `not_found` for the block it was hiding and so block
  its own accusation. Now Canary decides after the record pass. Once one of a server's
  records verifies under its pin, nothing that server answers stops the run, whatever its
  `/info` does. A refused record or list counts like an outage for that one block. A
  failed `/info` leaves only the server's policy unknown ([Errors](#errors)). A server
  whose `/info` answers as `canary-info/1` cannot stop the run either. Only a server that
  proves nothing still can: none of its records verifies, its `/info` gives no usable
  answer, and one of its answers is outside the API. No finding in that run could name it
  ([10. What these formats do not cover](#10-what-these-formats-do-not-cover)). A first
  version of this change, also dated 1 Oct, still required a usable `/info`. A withholder
  could leave `/info` unanswered and keep its veto, so that condition is gone.
  The same revision closes a second route. A receipt could sign a tip too high for
  Core's REST interface to read, and Core's refusal stopped the run. That tip now reads
  as a false chain claim, as [4. The retention rule](#4-the-retention-rule) always said.
  A slow server can still stretch the run
  ([10. What these formats do not cover](#10-what-these-formats-do-not-cover)).
- **One record can no longer cost the run a finding for every position it invents.** A
  record can sign any `n`. A server could sign `n` = 200,000 for one block, serve that
  many `absent` positions inside the window, and earn one finding each. That run took
  more than a minute. By extrapolation, a million positions would take about half an hour
  and write a state file of about 575 MB. Now a record that
  claims more entries than its block has transactions, not counting the coinbase, fails
  the record checks. It counts as no record, as a wrong network tag does. Canary also
  reads no more of a list than `n` positions can take, `4 + 66n` bytes. A longer answer
  counts as no list
  ([How canary check reaches a state](#how-canary-check-reaches-a-state-for-one-server-and-one-block)).
  It reads no more of a record than 4096 bytes, about six times an honest record, and
  keeps a record only when it passes the record checks. Before, a server could sign
  records padded with a 1 MiB tag. Canary kept every one until the run ended, and a
  review measured a 2.19 GB heap at 600 blocks. A full range would end the process before
  it saved anything ([`GET /commitment/{blockhash}`](#get-commitmentblockhash)).
- **Signet is refused.** `canary check` v1 accepts regtest and main. Every signet reports
  the same chain name to Bitcoin Core, so Canary cannot know which network magic to check
  against. Signet needs a flag that names the network, which is planned after v1
  ([9. The CLI](#9-the-cli)).

**Also 2026-10-01: `--withhold-txid` repeats.** The reference indexer now accepts the
switch more than once and withholds every txid named. The change is additive. It changes
no format and no version, and a single `--withhold-txid` behaves as before. Demo act 5
uses a second txid ([The withholding switch](#the-withholding-switch)).

This document pins every byte and field that the v1 programs exchange. The reference
indexer writes the tweak list and the receipt. `canary check` reads them and writes
evidence files and the state file. `canary verify`, `canary status`, `canary ui` and the
browser checker read those two files. Each program builds against this page, not against
another program's code.

It assumes you know Bitcoin and BIP-352, but not Canary's design. The
[design document](2026-09-06-canary-design.md) explains why each rule exists, and the
[glossary](../glossary.md) defines every term used here.

## What these formats let Canary claim

Canary makes tweak sourcing accountable. It does not remove the need to trust a server.
Every format below serves that narrower claim, under the conditions stated here.

- **Hiding only.** Canary looks for a server that leaves out an entry it signed for. It
  does not catch fake entries a server adds, which is a different attack
  ([Attacks explicitly out of scope](2026-09-06-canary-design.md#15-attacks-explicitly-out-of-scope)).
- **What v1 accuses.** v1 names a server as withholding in two cases only:
  - The server served a list that its own record contradicts. The list marks a signed-for
    entry `absent` inside the retention window, or excuses that gap with a chain claim the
    user's Bitcoin Core node contradicts. Or it differs from the record in length or root,
    or it fails to decode under a valid receipt.
  - A payment you declared is missing from the server's signed record. A record commits to
    every entry in the block, spent or not, so no policy explains the gap. Or the record
    includes the payment's entry, the list does not carry it in full, and Core shows one
    of its taproot outputs unspent, so pruning cannot explain the gap.

  A server that serves no record for the block, or signs a record and then serves no
  usable list, is not accused. v1 lists it as a warning ([findings](#findings)), because
  a missing record or an error response carries no signature. A server that declares no
  pruning and still sends an entry as a hash gets a warning too. Its policy comes from the
  unsigned `/info`, so nothing it signed shows the contradiction.
- **Two conditions.** The full claim holds given at least one honest index server
  publishing signed records, and an uncensored path to a relay carrying them. v1 fetches
  records over HTTP from each server. So a v1 finding against one server rests on that
  server's own signatures, and the cross-check between servers needs a second server.
- **Knowing is not proving.** A finding with an evidence file that carries a receipt can
  be checked offline by anyone. Every other finding is known to the person who ran
  `canary check`, and nobody else can confirm it from Canary's files. Each finding says
  which it is, in its `provable` field.
- **Servers disagree is not Data withheld.** Two different signed records for one block
  name two servers without saying which lied. Only Data withheld names one server.
- **Can't be checked is neither a pass nor an accusation.** It means Canary could not
  recompute a root for that block.

## 1. Conventions

### Terms used below

- An **entry** is one transaction's pair `(txid, tweak)`, 65 bytes. The design calls it a
  *leaf*.
- An **index server** computes entries for each block and serves them. Prose says
  *server*. The design calls it an *indexer*.
- A **signed record** is a server's signed Nostr event for one block. It carries the
  number of entries `n` and a 32-byte **root** over them. The design calls it a
  *commitment* ([The commitment object](2026-09-06-canary-design.md#33-the-commitment-object)).
- The **tweak list** is what a server returns for one block: `n` positions, each an
  entry, the entry's hash, or nothing.
- A **receipt** is the server's signature over one tweak list and the request that
  produced it.
- A block's **depth** is how far it sits below the server's tip, in blocks.

### Encodings

| Topic | Rule |
|---|---|
| Byte order | Txids and block hashes have two byte orders. **Internal order** is how the bytes appear in a serialized transaction or block header. **Display order** reverses them, as block explorers and `bitcoin-cli` print them. Binary formats and hash preimages use internal order. JSON, URLs and Nostr tags use display order. Each program converts in one place |
| Hex | Lowercase, no `0x` prefix. Writers emit lowercase and readers reject uppercase, so every value has one spelling |
| Base64 | RFC 4648 standard alphabet, with padding |
| Integers in binary layouts | Unsigned, little-endian |
| Times in JSON | RFC 3339 in UTC with a `Z` suffix, whole seconds: `2026-10-03T08:32:11Z` |
| Heights | Unsigned 32-bit integers. JSON carries them as numbers |
| Network | The 4-byte P2P message-start magic, read from btcd's `chaincfg.Params.Net`. Binary layouts carry its 4 little-endian bytes, which are the message-start bytes in wire order. JSON and the Nostr `network` tag carry the same value as a decimal `uint32` |

Canary knows three network magics by name. Any other magic prints as `unknown`.

| Name | Decimal (JSON) | Message-start bytes (binary) |
|---|---|---|
| `main` | 3652501241 | `f9beb4d9` |
| `signet` | 1087308554 | `0a03cf40` |
| `regtest` | 3669344250 | `fabfb5da` |

### Hashes, keys and signatures

**Tagged hash.** Every Canary hash is a BIP-340 tagged hash, the construction
[commit/hash.go](../../commit/hash.go) already uses:

```
TaggedHash(tag, m) = SHA-256( SHA-256(tag) ‖ SHA-256(tag) ‖ m )
```

| Tag | Hashes | Defined in |
|---|---|---|
| `canary/leaf/v1` | One entry: `txid ‖ tweak`, 32 + 33 = 65 bytes | [Merkle tree](2026-09-06-canary-design.md#32-merkle-tree) |
| `canary/node/v1` | Two child hashes, 64 bytes | [Merkle tree](2026-09-06-canary-design.md#32-merkle-tree) |
| `canary/root/v1` | `network ‖ block_hash ‖ n_le32 ‖ merkle_root`, 72 bytes | [Merkle tree](2026-09-06-canary-design.md#32-merkle-tree) |
| `canary/receipt/v1` | The receipt's first 114 bytes | [3. The receipt](#3-the-receipt), new in v1 |

**Keys.** Each server holds one secp256k1 key. Its 32-byte x-only public key is its Nostr
pubkey. The same key signs every signed record and every receipt. Signatures are 64-byte
BIP-340 Schnorr signatures. The client pins each server's pubkey by flag and never learns
it from the server ([Identity](2026-09-06-canary-design.md#36-identity)).

**Versions.** Every format names its version. A reader rejects a version it does not
know. It never guesses.

## 2. The tweak list

A server answers a request for one block with the tweak list. It holds exactly `n`
positions in canonical order, which is transaction order within the block. Every position
says what it carries, so the client never infers it. A list that merely stopped early
would look like a smaller block, and with one server nothing else would catch that
([Wire model](2026-09-06-canary-design.md#24-wire-model)).

| Offset | Size | Field | Encoding |
|---|---|---|---|
| 0 | 4 | `n` | uint32, little-endian |
| 4 | varies | `n` position records | In canonical order, back to back |

Each position record starts with a one-byte kind.

| Kind byte | Name | Payload | Record size | Meaning |
|---|---|---|---|---|
| `0x01` | `full` | `txid` (32 bytes, internal order) then `tweak` (33 bytes, compressed SEC) | 66 bytes | The entry itself |
| `0x02` | `hash` | `TaggedHash("canary/leaf/v1", txid ‖ tweak)`, 32 bytes | 33 bytes | The server pruned the entry and kept its hash |
| `0x03` | `absent` | None | 1 byte | Nothing. Permitted only outside the retention window ([4. The retention rule](#4-the-retention-rule)) |

**Reader rules.** A reader rejects the list if any of these hold:

1. `n` exceeds the bytes that follow it. The smallest record is 1 byte, so the reader
   checks this before it allocates anything.
2. A kind byte is not `0x01`, `0x02` or `0x03`.
3. A record runs past the end of the body.
4. Bytes remain after the `n`th record.

The list must also be exactly as long as the `n` in the server's signed record. That is a
comparison rule, not a decoding rule. [8. The state file](#8-the-state-file) says what a
mismatch produces.

**Size.** A list of `n` full entries is `4 + 66n` bytes. At `n ≈ 2000`, the order of a
mainnet block, that is 132,004 bytes, about 129 KiB. An empty block is the 4 bytes
`00000000`. No list of `n` positions is longer, so `canary check` reads at most `4 + 66n`
bytes, with `n` from the server's valid record. A longer answer counts as no list.

**Example.** Three positions: entry 0 in full, position 1 absent, entry 2 in full. The size
is 4 + 66 + 1 + 66 = 137 bytes.

```
03000000                                                            n = 3
01 75d59e36a1e1ccbbd5a47f129b923047268c580d6a09a9d63c3084bd397166ae   position 0: full, txid
   03f9a5befd0ea1dbba15e6ccba383fbdbc750a0f637698a06fa47c6823044e09eb     tweak
03                                                                  position 1: absent
01 3f692f812332917a1bc7cafd01d5d02a7bf2b4c25bb4f5d7211b670610c0e0b8   position 2: full, txid
   0362573ab3eb6eccc73071623c211f41b392bf29edcb9fabe7aa9addeb4bbd6ab9     tweak
```

The first txid is internal order. A block explorer prints it as
`ae667139bd84303cd6a9096a0d588c264730929b127fa4d5bbcce1a1369ed575`.

## 3. The receipt

A signed record says what exists in a block. A receipt says what the server gave you. The
same key signs both, so an entry that is in the record and missing from the receipted list
is a contradiction inside the server's own signatures
([Receipts](2026-09-06-canary-design.md#38-receipts)).

The server signs a receipt for every tweak list it serves. A receipt is 178 bytes:

| Offset | Size | Field | Encoding | Why it is signed |
|---|---|---|---|---|
| 0 | 1 | `version` | `0x01` | Lets v2 change the layout without ambiguity |
| 1 | 4 | `network` | Message-start bytes | Stops a receipt from one chain being presented as one from another |
| 5 | 1 | `resource` | `0x01` = tweak list | Keeps a v2 receipt for filters or output data from passing as a receipt for a tweak list |
| 6 | 32 | `block_hash` | Internal order | Names the block the list is about |
| 38 | 8 | `dust_sat` | uint64, little-endian | The dust threshold the client asked for and the server applied. `0` means none. Without it, a server could answer with an older, differently filtered list |
| 46 | 4 | `tip_height` | uint32, little-endian | The height of the server's best block when it served. The retention rule measures depth from it |
| 50 | 32 | `tip_hash` | Internal order | The hash of that block. It ties the tip to one chain ([4. The retention rule](#4-the-retention-rule)) |
| 82 | 32 | `body_sha256` | Plain SHA-256 of the exact response body | Binds the receipt to the bytes. Plain SHA-256 lets anyone check it with `sha256sum` |
| 114 | 64 | `sig` | BIP-340 Schnorr signature | Signs `digest` below |

The size is 1 + 4 + 1 + 32 + 8 + 4 + 32 + 32 + 64 = 178 bytes.

**Digest.** The signature covers every byte before it:

```
digest = TaggedHash("canary/receipt/v1", receipt[0:114])
sig    = BIP340Sign(server_secret_key, digest)
```

The receipt carries no public key. The client checks the signature against the key it
pinned for that server. Carrying the key in the receipt would invite a client to trust
whatever key arrived with it.

**Transport.** The server sends the receipt in an `X-Canary-Receipt` response header,
next to the body it signs. The value is the 178 bytes as lowercase hex, 356 characters.

Hex wins over base64 for three reasons. Every other hash, key and signature in Canary is
already hex, including Nostr ids and pubkeys, so readers need one decoder. Hex has no
alphabet or padding variants to disagree on. And `xxd -r -p` turns it back into bytes
for anyone checking by hand. It costs 116 more characters than base64, which is well
inside the 8 KiB header limit most HTTP servers apply.

**What the client checks.** When `canary check` receives a list with a receipt, it
checks all of these. If any fails, it treats the list as unsigned: it can still act on
what it saw, but it cannot prove it to anyone.

1. The header decodes to 178 bytes and `version` is `0x01`.
2. `sig` is valid for `digest` under the server's pinned pubkey.
3. `network` matches the local Bitcoin Core node's network.
4. `resource` is `0x01`.
5. `block_hash` is the block the client asked for.
6. `dust_sat` is the threshold the client asked for.
7. `body_sha256` equals the SHA-256 of the body the client received.

It checks the signed tip separately, and only where the retention rule needs it
([4. The retention rule](#4-the-retention-rule)).

**Example.** The receipt for the 137-byte list in [2. The tweak list](#2-the-tweak-list).
An example key made for this page signed it. Nobody should use that key.

```
X-Canary-Receipt: 01fabfb5da01b809dc22838a13852fcf3deead2c3427ba0781d87fab1789c3d9a7cfb364fbca0000000000000000d4000000d2311c5f151c5222bd9bcc59dbcc55fb7375ce61792dc71d6dd8691687c45b8fa1b3b064b0286290f4b87ac6915a523301f0b4977ea3b04d3663df60bcc707c9b3f5f6f98dddbd7080322b8e42a6384d00841fba8e69dc37687cd492830379bfedd2111778f28cb1ea58c0b1ec183ce7e4c8aeb1e1d34eb03f090df07139ed0b
```

| Field | Value | Read as |
|---|---|---|
| `version` | `01` | Version 1 |
| `network` | `fabfb5da` | regtest |
| `resource` | `01` | Tweak list |
| `block_hash` | `b809dc22…fbca` | Display order `cafb64b3cfa7d9c38917ab7fd88107ba27342cadee3dcf2f85138a8322dc09b8` |
| `dust_sat` | `0000000000000000` | 0, no threshold |
| `tip_height` | `d4000000` | 212 |
| `tip_hash` | `d2311c5f…5b8f` | Display order `8f5bc4871669d86d1dc72d7961ce7573fb55ccdb59cc9bbd22521c155f1c31d2` |
| `body_sha256` | `a1b3b064…07c9` | SHA-256 of the 137-byte list |
| `sig` | `b3f5f6f9…ed0b` | Valid under pubkey `b1070620799e7da6bbc296ec7ea6aacf7f027317af796abf35f0c9c83710270d` |

The `digest` for this receipt is
`b4d40cabc899c628f452b60d05b80f3c68e85aac6dceb9ceeec21b875ec5e9e6`.

## 4. The retention rule

**Rule.** A position marked `absent` while its block is less than 144 blocks below the
server's signed tip is an omission. Canary names that server and marks the block
**Data withheld**. The state code is `compromised`, and the reason is `absent_in_window`.

The [wire model](2026-09-06-canary-design.md#24-wire-model) requires a server to keep at
least an entry's hash for its 144 most recent blocks. This rule turns that requirement
into a check ([Comparison procedure](2026-09-06-canary-design.md#25-comparison-procedure)).
The window is a protocol constant. No server can declare its own. The rule needs the
server's signed record, for the block height and for `n`. A block with no record from that
server reads Not checked instead.

**Depth.** Canary computes depth from two values the server signed with the same key:

```
depth  = tip_height − block_height
inside = depth < 144
```

- `tip_height` comes from the receipt that covers the list.
- `block_height` comes from the `height` tag of the server's signed record for that block.
- Depth 0 is the tip itself, and depth 143 is the oldest block inside the window. So the
  window holds 144 blocks.
- A negative depth means the server served a block above its own signed tip. Canary
  treats it as inside the window, so a server cannot escape the rule by understating its
  tip.

In the example, the record says height 205 and the receipt says tip 212. The depth is
212 − 205 = 7, which is inside. The same block would leave the window when the server's
tip reached 205 + 144 = 349.

**Only `absent` breaks the rule.** A `hash` position keeps the entry's hash, so it meets
the rule, and the root still recomputes. That is the hash-only variant in
[10. What these formats do not cover](#10-what-these-formats-do-not-cover). A server whose
`/info` declares no pruning still gets a `hash_without_policy` warning for it
([Reasons](#reasons)), but no accusation.

**Filling still happens first.** The rule names the server before any root is
recomputed. Canary still tries to recover the missing entry and still recomputes the root
before it records a block's state. The recovered entry tells you which transaction was
left out, and the Merkle proof ties it to the server's signed root. A block whose root was
never recomputed is never marked Checked.

**Why the tip must be signed.** The rule depends on how deep the block was when the
server answered. By the time anyone reads an evidence file, every block in it is deep. So
the serve-time depth has to travel inside something the server signed, for four reasons:

- The signed record's height says where the block is. It says nothing about when the
  server served it.
- Nostr's `created_at` is self-asserted and can be backdated. Nostr gives publication, not
  timestamping ([What we do not trust about Nostr](2026-09-06-canary-design.md#35-what-we-do-not-trust-about-nostr)).
- The HTTP `Date` header is unsigned.
- With the tip in the receipt, one file holds the whole contradiction. The record puts the
  block at height 205. The receipt puts the tip at 212 and shows position 1 absent. A
  stranger needs nothing outside the file to check it.

**Why the tip hash as well as the height.** A server could try to overstate its tip, so
the block looks 144 or more blocks deep and `absent` looks permitted. The signed hash makes
that claim checkable. The server must name a specific block at that height, and anyone
with a node can see whether that block is on their chain
([Chain agreement](2026-09-06-canary-design.md#46-chain-agreement)).

**Where Bitcoin Core comes in.** Canary applies the rule to the server's own signed values
first. It consults its local Bitcoin Core node only when those values put the block
outside the window.

- **Inside the window by the signed values.** The position is an omission, whatever Core
  says. An honest server never signs a tip and a height that convict it, so a wrong tip,
  or one ahead of Core, changes nothing here. `canary verify` applies the same test to the
  same signed values, so the two commands give the same answer for the same bytes.
- **Outside the window by the signed values.** The server's only excuse for the gap is its
  own chain claim, so Canary checks that claim against Core. "Within 6 blocks of Core's
  tip" below means `|tip_height − core_tip_height| ≤ 6`.

| What Core shows | Result for the position |
|---|---|
| The record's height is Core's height for this block hash, and Core's block at `tip_height` has the hash `tip_hash` | **Confirmed.** The absence is permitted, and Canary tries to fill the position |
| The record's height is not Core's height for this block hash | **False chain claim.** A block hash has one height forever, so no reorg explains this. The block reads **Data withheld**, reason `false_chain_claim` |
| `tip_height` is more than 6 blocks from Core's tip, and Core has no block with hash `tip_hash` at that height | **False chain claim**, as above |
| `tip_height` is within 6 blocks of Core's tip, and Core has no block with hash `tip_hash` at that height | **Unconfirmed.** A reorg near the tip, or a Core node a block or two behind, can explain it. If nobody fills the position, the block reads **Can't be checked**, reason `tip_unconfirmed`. The next run checks again with a fresh receipt |

A `tip_height` above 2,147,483,647 counts as a height where Core has no block. Core's REST
interface refuses such a height outright, so `canary check` answers it without asking.
A server cannot stop the run by signing one.

The 6-block margin is the one [Chain agreement](2026-09-06-canary-design.md#46-chain-agreement)
uses to tell a reorg from a lie. It also bounds what an unconfirmed tip buys a withholder.
The claimed tip can sit at most 6 blocks past Core's tip and must still be at least 144
blocks above the block. So the block is already at least 144 − 6 = 138 blocks below Core's
tip, and it leaves the window within 6 more blocks anyway.

A false chain claim is a signed statement that the user's node contradicts. v1 accuses on
it but cannot prove it to others: checking it needs a node, and `canary-evidence/1` has no
claim for it. So its finding records `"provable": false` and no evidence file.

`canary check` needs a Core node that has finished its initial sync, or honest tips would
look false. It reads Core's `initialblockdownload` flag and exits with code 5 while the
flag is true.

**Without a receipt.** If the list arrived with no valid receipt, there is no signed tip.
Canary measures depth from its own Core tip and Core's height for the block instead. It
still marks an `absent` position inside the window Data withheld, because it saw the list
itself. But the finding is not provable to others, and the state file records
`"provable": false`.

## 5. Reference indexer HTTP API

`canary-indexer` is the v1 reference indexer. It reads a regtest Bitcoin Core node,
computes each block's entries with the `canonical` package, signs one record per block,
and serves the three routes below.

| Route | Returns | Content type |
|---|---|---|
| `GET /info` | What the server declares about itself. Unsigned | `application/json` |
| `GET /commitment/{blockhash}` | The signed record for one block, as the raw Nostr event | `application/json` |
| `GET /tweaks/{blockhash}` | The tweak list for one block, with a receipt header | `application/vnd.canary.tweaks.v1` |

**Block hashes in URLs use display order**: 64 lowercase hex characters, exactly as
`bitcoin-cli getblockhash` prints them and as the record's `b` tag holds them. The server
converts to internal order once, at the edge. Paths name blocks by hash, never by height,
because the same height can name different blocks on two chains
([Comparison procedure](2026-09-06-canary-design.md#25-comparison-procedure)). The client
maps height to hash with its own Core node.

All three routes accept `GET` and `HEAD` only.

### `GET /info`

The server's self-description. The server signs none of it, so Canary uses it for display and
routing, never as evidence. The signed tip is the one in each receipt, and the pubkey that
counts is the one the client pinned.

| Field | Type | Meaning |
|---|---|---|
| `format` | string | `canary-info/1` |
| `software` | object | `name`, `version` and `build` of the server program |
| `network` | object | `name` and `magic`, as in [1. Conventions](#1-conventions) |
| `pubkey` | hex, 32 bytes | The key the server says it signs with. A convenience only |
| `tip` | object | `height` and `hash` (display order) of the server's best block. Unsigned |
| `start_height` | number | The first height the server has indexed |
| `retention_window` | number | Always `144`. Informational, because the window is a protocol constant |
| `policy` | object | The server's declared subtractions: `prunes_spent` (bool), `dust_threshold_sat` (number), `dust_configurable` (bool). Unsigned in v1 |
| `record_kind` | number | `1352`, the Nostr kind of its signed records |
| `signs_receipts` | bool | Whether `/tweaks` responses carry `X-Canary-Receipt` |

### `GET /commitment/{blockhash}`

The body is the signed kind-1352 event, exactly as the server signed it: `id`, `pubkey`,
`created_at`, `kind`, `tags`, `content` and `sig`. The server stores the event when it
indexes the block and returns that same event on every request. It never re-signs a block,
because two different records for one block from one key contradict each other. The
response carries `Cache-Control: public, max-age=31536000, immutable`.

[The commitment object](2026-09-06-canary-design.md#33-the-commitment-object)
and `feed.ToEvent` fix the event's tags:

| Tag | Value |
|---|---|
| `b` | Block hash, display order. The only tag a relay indexes |
| `height` | Block height, decimal |
| `n` | Number of entries, decimal |
| `network` | Network magic, decimal |
| `policy_ref` | Event id of a signed policy declaration. v1 publishes none, so it is 64 zeros |
| `root` | The root, hex. It must equal `content` |

The [evidence file example](#example) carries a complete event.

**Size.** The reference indexer's record for a regtest block is 689 bytes. The tags'
decimal values and `created_at` can grow by about 30 bytes at most, so an honest record
stays under 720 bytes. `canary check` reads at most 4096 bytes of a record, and a longer
answer counts as no answer: **Not checked**, reason `server_unreachable`. The limit
matters because a server can sign extra tags into its own record, and the record still
verifies. Canary keeps each valid record until the run ends, so without the limit a
server could grow the run's memory by any amount per block. It keeps no record that fails
the record checks.

### `GET /tweaks/{blockhash}`

| Part | Value |
|---|---|
| Query | `dust_sat`, optional, a decimal number of satoshis. Absent means `0`. The v1 reference indexer accepts only `0` and says so in `/info` with `"dust_configurable": false`. `canary check` always asks for `0`, because it checks the full list, not a wallet's view |
| Body | The tweak list, [2. The tweak list](#2-the-tweak-list) |
| `Content-Type` | `application/vnd.canary.tweaks.v1` |
| `X-Canary-Receipt` | The receipt as hex, [3. The receipt](#3-the-receipt) |
| `Cache-Control` | `no-store`, because the receipt carries the current tip |

### Errors

Every error is JSON with one shape. An error response carries no receipt, so it proves
nothing about the server.

```json
{ "error": { "code": "unknown_block", "message": "No block with this hash in this server's index.", "error_id": null } }
```

| Status | `code` | When | What `canary check` records |
|---|---|---|---|
| 400 | `bad_block_hash` | The path segment is not 64 lowercase hex characters | An answer outside the API, described under this table |
| 400 | `unsupported_parameter` | `dust_sat` is not a number, or a value the server does not support | An answer outside the API, described under this table |
| 404 | `unknown_block` | The server has not indexed a block with this hash | On `/commitment`: **Not checked**. The reason is `not_indexed_yet` if the server's tip is below the block. It is `no_record_for_block` if the server signed records for a lower and a higher block in this run, and `no_records` otherwise. On `/tweaks` after a record: **Can't be checked**, `list_not_served` |
| 404 | `not_found` | Any other path | An answer outside the API, described under this table |
| 405 | `method_not_allowed` | Any method other than `GET` or `HEAD` | Not used by Canary |
| 500 | `internal` | The server failed. `error_id` names the line in its log | On `/commitment`: **Not checked**, `server_unreachable`. On `/tweaks` after a record: **Can't be checked**, `list_not_served` |
| 503 | `not_ready` | The server has not finished its first sync | On `/commitment`: **Not checked**, `server_unreachable`. On `/tweaks` after a record: **Can't be checked**, `list_not_served` |

**Answers outside the API.** `canary check` never sends a request that earns
`bad_block_hash`, `unsupported_parameter` or `not_found` from a v1 server. It records such
an answer like an outage. In all but one case, below, the run goes on and saves everything
it gathered.

- **On `/commitment`** the block reads **Not checked** for that server, reason
  `server_unreachable`.
- **On `/tweaks`** the block reads **Can't be checked**, reason `list_not_served`, with the
  warning when the block is inside the window. Canary asks for a list only after a valid
  record, so this case always continues.
- **On `/info`** the server declares no policy in this run, the same as when `/info` gives
  no answer, `internal` or `not_ready`. Its `servers[]` entry has `reachable: false` and
  `policy: null`. Its `error` says the policy is unknown, unless a later error replaced
  it. The terminal prints the `/info` error either way. The dashboard shows the policy as
  unknown, never as not declared, and counts the server as having answered if it served
  a valid record, a receipt, or a list.

A server's answers stop the run in one case only, with exit code 5 and nothing saved.
None of the server's records verified under its pinned key, its `/info` gave no
`canary-info/1` answer, and at least one of its answers was outside the API. Canary then
can't tell a hostile server from a wrong `--indexer` URL, a wrong pin or a bug in Canary,
and a wrong URL is the likelier. A record that verifies proves the URL reaches the server
the pin names. That holds even when the record then fails on its `n`, as step 1 of
[How canary check reaches a state](#how-canary-check-reaches-a-state-for-one-server-and-one-block)
describes. A `canary-info/1` answer shows the URL reaches a v1 server. A server that
gave no answer at all is an outage, not a wrong URL, so the run goes on.

`canary check` makes that decision once it has asked for every block's record, so the
order of the blocks never decides it. Until 2026-10-01 every such answer stopped the run.
A withholding server could then answer `not_found` for the block it was hiding, and the
run that would have named it saved nothing.

A server that signed a record for a block and then refuses the list is not silent. The
refusal is an error the client sees, so Canary marks that server's result Can't be checked
rather than Checked. Inside the retention window it also lists a warning against the server
([findings](#findings)). An error response carries no receipt, so v1 cannot prove the
refusal and does not accuse on it. The block can still read Checked when another server's
list checks out, and the warning keeps the refusal visible.

### The withholding switch

`canary-indexer --withhold-txid <txid>` makes the reference indexer misbehave on purpose,
for the demo. It still signs an honest record for every block. When it serves the block
holding that txid, it marks the entry's position `absent` and signs a receipt over that
list. It prints a warning at start-up, and its `--help` describes the switch.

`/info` does not reveal the switch. Canary must catch the server without the server
confessing.

The switch can be given more than once. The server then withholds every txid named, in
whichever blocks hold them, and its start-up warning names each one. Demo act 5 uses this
for its Can't be checked block:

- The second txid is a payment whose block sits 144 or more blocks below the server's
  signed tip, so its gap is outside the window. The user's Core node confirms that tip.
- A check that pins only this server, and has no `--expect` for that payment, has no other
  source for the entry. The block reads Can't be checked, reason `gap_unfilled`. That is
  neither a pass nor an accusation, and the run lists no finding.
- The main check is unchanged. Its payment's block is inside the window and still reads
  Data withheld, reason `absent_in_window`.

The demo's optional branch scene needs a different switch, and these formats do not freeze
one. In that scene the attacker signs a record that leaves the entry out, and a second,
honest server's root differs from it, so the block reads Servers disagree. If the switch is
built, it is additive, prints the same start-up warning and has the same visible help text.
Run that scene without `--expect` for the payment. A declared payment turns the block into
Data withheld, reason `expected_payment_not_in_record`, which outranks Servers disagree.

## 6. The evidence file

An evidence file is one JSON document that lets anyone check a Data withheld finding
offline. `canary check` writes one for each finding where it recovered the left-out entry
and the case fits the one claim this format makes. Before writing a file, `canary check`
runs it through the same code as `canary verify`. It writes the file only if the result is
Checks out, or Checks out, inclusion only.
The format is `canary-evidence/1`, and its only claim is `omission`: the server signed a
record containing an entry, then served a list that did not carry it.

### Fields

| Field | Type | Meaning |
|---|---|---|
| `format` | string | `canary-evidence/1` |
| `claim` | string | `omission`. v1 defines no other claim |
| `accused` | hex, 32 bytes | The accused server's pubkey |
| `network` | object | `magic` (decimal) and `name`. `verify` names the network from the magic and ignores `name`, which is there for people reading the raw file |
| `block` | object | `hash` (display order) and `height`, both as the signed record states them |
| `commitment_event` | object | The server's signed record: the raw kind-1352 event, every field as served |
| `receipt` | hex or `null` | The `X-Canary-Receipt` value exactly as received, 356 characters |
| `served_base64` | base64 or `null` | The exact body of the `/tweaks` response. `receipt` and `served_base64` are both present or both `null` |
| `missing` | object | The left-out entry: `txid` (display order) and `tweak` (66 hex characters, compressed SEC) |
| `proof` | object | Merkle proof of the entry in the signed root: `index` (its position), `n`, and `siblings` (hex hashes, bottom-up) |
| `context` | object | For people only. `verify` never reads it. Optional keys: `server_label`, `server_url`, `found_by` (`other_server` or `expected_payment`), `written_by`, `written_at` |

**No result field.** The file carries no stored outcome, and `verify` never reads one.
Every result comes from recomputation. A reader rejects an unknown field at every level as
malformed: at the top level, and inside `network`, `block`, `commitment_event`, `missing`,
`proof` and `context`. So nobody can add a field that a careless tool would echo. The
`context` values are strings the file's author typed, and nothing checks them. A screen
that shows them labels them as unchecked notes and keeps them outside the verify result.

**Names.** `canary check` names each file
`omission-<network>-<height>-<txid first 8 hex>-<pubkey first 8 hex>.json`, for example
`omission-regtest-205-01982d71-b1070620.json`. The txid prefix is display order.
Evidence does not expire, so `canary check` never overwrites a file that carries a receipt.
A file without a receipt proves less, so a later run may replace it with a file that
carries a receipt and checks out. Canary writes the new file to `<name>.tmp` and renames
it over the old one.

**Size.** The served bytes dominate. A 3-entry list is 137 bytes. At `n ≈ 2000` the list is
132,004 bytes, which base64 turns into 176,008 characters. Base64 costs a third more than
the raw bytes, where hex would double them.

### What `canary verify` recomputes, in order

`canary verify` reads one file and opens no network connection. It runs these steps in
order and stops at the first failure. Steps 1 to 5 need no receipt. Steps 6 to 8 need one.
So a file without a receipt runs the same first five steps and stops at a smaller result.

This order and the field list above are the exact form of the design's
[Evidence artifact](2026-09-06-canary-design.md#47-evidence-artifact) section, which
points here.

| # | Step | What `verify` recomputes | Fails with |
|---|---|---|---|
| 1 | `read` | The file parses as JSON with no unknown fields. `format` is `canary-evidence/1` and `claim` is `omission`. Every value has the right type and length. `receipt` and `served_base64` are both present or both `null` | `ErrMalformed`, `ErrUnsupportedFormat` |
| 2 | `record_signature` | The event id recomputed from the event's fields matches `id`. The BIP-340 signature is valid. The kind is 1352, every tag is present, and the `root` tag equals `content` | `ErrBadSignature` for the id or signature. `ErrMalformed` for kind or tags |
| 3 | `signer` | The event's `pubkey` equals `accused` | `ErrSignerMismatch` |
| 4 | `block` | The `b` tag equals `block.hash`. The `height` tag equals `block.height`. The `network` tag equals `network.magic` | `ErrBlockMismatch` |
| 5 | `inclusion` | `proof.n` equals the record's `n`. The proof carries `missing` to the signed root, using `commit.VerifyProof` with the record's network, block hash and root | `ErrProofInvalid` |
| 6 | `receipt` | The receipt is 178 bytes with version 1. Its signature is valid under `accused`. Its network and block hash equal the record's. Its resource is the tweak list. Its `body_sha256` equals the SHA-256 of the decoded `served_base64` | `ErrMalformed` for length or version. `ErrReceiptInvalid` for the rest |
| 7 | `served_list` | The served bytes decode under [the reader rules](#2-the-tweak-list). The list has `n` positions. Position `proof.index` does not carry the entry: it is `absent`, holds a different entry, or holds a hash other than the entry's hash | `ErrMalformed` if undecodable. `ErrBlockMismatch` if the length differs from `n`. `ErrEntryServed` if the position carries the entry or its hash |
| 8 | `window` | If the position is `absent`: `tip_height − block.height < 144`, from the receipt and the record. If the position holds different data, the step passes, because different data at a committed position is never permitted | `ErrNotInWindow` |

The `claim` field only selects which steps run. The result is whatever the steps produce,
never what the file says about itself.

Step 8 needs no node and never reads `tip_hash`. A server never signs a tip and a height
that convict it, so signed values that put the block inside the window settle the
question. The tip hash matters only when the signed values put the block outside the
window. `canary check` then consults Core ([4. The retention rule](#4-the-retention-rule)),
and it writes no evidence file for that case.

### The three outcomes

| Outcome | When | First line printed |
|---|---|---|
| **Checks out** | Steps 1 to 8 all pass | `Checks out.` |
| **Checks out**, inclusion only | Steps 1 to 5 pass and the file has no receipt | `Inclusion only: you can be sure of this, you can't yet prove it to others.` |
| **Does not check out** | A step from 2 to 8 fails with anything other than `ErrMalformed` or `ErrUnsupportedFormat` | `Does not check out: <step> failed.` |
| **Can't read this file** | The file is missing or not JSON, or a step fails with `ErrMalformed` or `ErrUnsupportedFormat` | `Can't read this file: <reason>.` |

Inclusion only is the Checks out outcome with a smaller claim. For it, `verify` prints two
more lines under the first:

```
Inclusion only: you can be sure of this, you can't yet prove it to others.
The server signed a record that includes this entry. This file has no receipt, so it cannot show what the server sent.
If your own canary check wrote this file, it saw the entry left out. Anyone else sees only that the entry was signed for.
```

A **Does not check out** result says the file's claim fails. It does not say the accused
server is honest.

## 7. VerifyReport and error codes

`canary verify --json`, `canary ui` and the browser checker all return one JSON object,
built by one Go function in the `evidence` package. The CLI, the dashboard and the browser
therefore always agree.

| Field | Type | Meaning |
|---|---|---|
| `result` | string | `checks_out`, `does_not_check_out` or `unreadable` |
| `code` | string | `ok`, `inclusion_only`, or an error code from the table below |
| `message` | string | One plain sentence for people, taken from the shared wording table |
| `format` | string or `null` | The file's `format`, as read |
| `claim` | string or `null` | The file's `claim`, as read |
| `accused` | object or `null` | `pubkey` (hex) and `npub` (bech32, for display) |
| `network` | object or `null` | `magic` and the `name` verify derived from it |
| `block` | object or `null` | `hash` and `height` |
| `missing` | object or `null` | `txid`, `tweak` and `index` |
| `commitment_event_id` | hex or `null` | The record's event id |
| `has_receipt` | bool | Whether the file carries a receipt |
| `receipt_tip` | object or `null` | `height` and `hash` (display order) from the receipt, so a reader with a node can check the tip |
| `checks` | array | One object per step, in order: `step` (the name from the table above), `ok` (`true`, `false`, or `null` when the step did not run) and `text` (one sentence) |

A field is `null` when verify stopped before it could read that value. `checks` always
lists all eight steps. A step after a failure has `"ok": null` and the text
`Not run: an earlier step failed.` A receipt step in a file without a receipt has
`"ok": null` and the text `Not run: this file has no receipt.`

### Error codes

Each code has a Go sentinel error in the `evidence` package. Callers match with
`errors.Is`. Error strings follow `evidence: <what failed>: <detail>`.

| Sentinel | `code` | `result` | Meaning |
|---|---|---|---|
| `ErrMalformed` | `malformed` | `unreadable` | Not JSON, an unknown field, a wrong type or length, or bytes that do not decode |
| `ErrUnsupportedFormat` | `unsupported_format` | `unreadable` | A `format` other than `canary-evidence/1`, or a `claim` other than `omission` |
| `ErrBadSignature` | `bad_signature` | `does_not_check_out` | The record's id or signature is invalid |
| `ErrSignerMismatch` | `signer_mismatch` | `does_not_check_out` | The record was signed by a key other than `accused` |
| `ErrBlockMismatch` | `block_mismatch` | `does_not_check_out` | The record, the file or the served list disagree about the block, its height, its network or its `n` |
| `ErrProofInvalid` | `proof_invalid` | `does_not_check_out` | The Merkle proof does not carry the entry to the signed root |
| `ErrReceiptInvalid` | `receipt_invalid` | `does_not_check_out` | The receipt's signature, network, block hash, resource or body digest does not match |
| `ErrEntryServed` | `entry_served` | `does_not_check_out` | The served list carries the entry, or its correct hash, at that position |
| `ErrNotInWindow` | `not_in_window` | `does_not_check_out` | The position is absent, but the block was 144 or more blocks below the signed tip, where absence is permitted |

`ErrEntryServed` is a ninth sentinel, added to the eight planned before this page. None of
those eight could name the case where the served list does carry the entry, and that case
needs its own wording on screen.

## 8. The state file

`canary check` writes one JSON file per run. `canary status` prints it, `canary status
--json` prints it unchanged, and `canary ui` renders it. The format is `canary-state/1`.

### Top level

| Field | Type | Meaning |
|---|---|---|
| `format` | string | `canary-state/1` |
| `generated_at` | time | When the run finished. The dashboard shows results as stale from this time |
| `canary` | object | `version` (for example `0.1.0`) and `build` (the git commit, for example `abc1234`). The build id is `<version>+<build>` |
| `network` | object | `name` and `magic` of the Core node Canary checked against |
| `chain_tip` | object | `height`, `hash` (display order) and `source` (`core` in v1) at the time of the run |
| `checked` | object | `from` and `to`, the inclusive height range this run covered |
| `evidence_dir` | string | Absolute path of the directory holding evidence files |
| `servers` | array | One object per configured server |
| `coverage` | array | Run-length ranges of block states, keyed by height |
| `counts` | object | Number of blocks in each state. All six keys are always present |
| `blocks` | array | Per-block detail, keyed by hash, one entry per block in `checked` |
| `findings` | array | Every finding from earlier runs whose block Core still knows, plus this run's. See [findings](#findings) |
| `expected_payments` | array | Payments the user declared with `--expect`, and what each server did with them |

### `servers[]`

| Field | Type | Meaning |
|---|---|---|
| `label` | string | The label from `--indexer`. Unique within one file. Letters `a-z`, digits and `-`, at most 32 characters |
| `url` | string | Base URL |
| `pubkey` | hex or `null` | The pinned pubkey. `null` when pinned as `none`, for a server that signs nothing |
| `publishes_records` | bool | Whether the server returned a valid signed record for any block in this run |
| `signs_receipts` | bool | Whether any list in this run arrived with a valid receipt |
| `reachable` | bool | Whether `/info` answered as `canary-info/1` in this run. A server can read `false` here and still serve valid records and lists ([Errors](#errors)) |
| `tip` | object or `null` | `height`, `hash` and `signed` (true when taken from a valid receipt, false when taken from `/info`) |
| `policy` | object or `null` | The `policy` object from `/info`, plus `"signed": false`. v1 policies are unsigned |
| `error` | string or `null` | The last error, in plain words |

### States and on-screen labels

Six state codes. The code is stable and never shown. The label is what every screen
prints, from the shared wording table.

| Code | Label | Meaning |
|---|---|---|
| `verified` | Checked | The root recomputed over all `n` positions and matched the signed record, and no position needed filling. It means the tweak list was checked, never that payments were |
| `resolved` | Checked, gap filled | As `verified`, but some positions came as hashes or were filled from another source before the root was recomputed |
| `unresolvable` | Can't be checked | Canary could not recompute the root. Neither a pass nor an accusation |
| `unverified` | Not checked | There was no signed record to check against. The data may still be fine. Nothing about it was checked |
| `disputed` | Servers disagree | Two servers signed different records for the same block hash. At least one lied, and Canary does not know which |
| `compromised` | Data withheld | One named server left out an entry it had signed for, or left out the entry for a payment you declared |

### Reasons

Every state carries a reason code. The dashboard explains each one.

| State | Reason | What happened |
|---|---|---|
| `verified` | `records_agree` | Two or more servers signed the same root, and a served list matches it |
| `verified` | `expected_payment` | One server's list matches its record and carries a payment you declared |
| `verified` | `own_record` | One server's list matches the record it signed. Nothing checks that the record itself is complete. A second server or a declared payment would |
| `resolved` | `filled_from_server` | Another server supplied the entry, and it proved into this server's root |
| `resolved` | `filled_from_expected_payment` | Canary computed the entry from a payment you declared, and it proved into the root |
| `resolved` | `hash_retained` | The server sent some entries only as hashes. The root matches. Canary cannot tell pruning from hiding here. A server that declared no pruning also gets a `hash_without_policy` warning |
| `unresolvable` | `gap_unfilled` | A position is absent outside the retention window, Core confirms the server's chain claim, and nobody supplied the entry |
| `unresolvable` | `tip_unconfirmed` | A position is absent, the server's signed tip puts the block outside the window, and that tip is within 6 blocks of Core's tip but not on Core's chain. Nobody supplied the entry ([4. The retention rule](#4-the-retention-rule)) |
| `unresolvable` | `list_not_served` | The server signed a record but did not serve the list. Inside the window this also raises a warning |
| `unresolvable` | `list_unreadable` | A list with no valid receipt failed [the reader rules](#2-the-tweak-list). Inside the window this also raises a warning. A list with a valid receipt that fails them gives `served_contradicts_record` instead |
| `unverified` | `no_records` | The server signed no record for this block, and it did not sign records on both sides of it in this run. It may sign nothing, or may have started indexing above this block |
| `unverified` | `no_record_for_block` | The server signed records for a lower and a higher block in this run, but not this one. This also raises a warning. v1 does not accuse on it |
| `unverified` | `not_indexed_yet` | The server's tip is below this block |
| `unverified` | `server_unreachable` | The server did not answer, or answered `internal` or `not_ready`. It also covers a record request answered outside the API, in a run that goes on ([Errors](#errors)) |
| `disputed` | `records_differ` | Two servers signed different roots for this block hash |
| `compromised` | `absent_in_window` | A position was absent inside the retention window ([4. The retention rule](#4-the-retention-rule)) |
| `compromised` | `false_chain_claim` | A position was absent, and the server excused it with a signed height or tip that Core contradicts ([4. The retention rule](#4-the-retention-rule)) |
| `compromised` | `served_contradicts_record` | The list's length differs from the record's `n`, a list with a valid receipt fails the reader rules, or the recomputed root differs from the signed root |
| `compromised` | `expected_payment_not_in_record` | The server's signed record leaves out the entry for a payment you declared. Canary recomputed the record's root, and no position holds the entry or its hash. A record commits to every entry in the block, spent or not, so Canary checks nothing about spending. Found by the tripwire |
| `compromised` | `expected_payment_not_in_list` | The record includes a declared payment's entry, but the list does not carry it in full: it sends only the hash, or marks the position absent outside the retention window. Core shows one of the payment's taproot outputs unspent, at or above the server's declared dust threshold, so pruning cannot explain it. Found by the tripwire |

One reason is a warning only. It never becomes a server's or a block's reason, so it has no
state.

| Reason | What happened |
|---|---|
| `hash_without_policy` | The server's `/info` declared no pruning (`"prunes_spent": false`), yet its list sent at least one position as a hash. `canary check` always asks for `dust_sat=0`, so the dust threshold cannot explain a hash either. v1 policies are unsigned, so this is a warning, never an accusation. The server's own result for the block keeps its reason, usually `hash_retained`. A server whose `/info` gave no `canary-info/1` answer declared nothing and gets no such warning |

"Inside the window" for a warning is measured from Core's tip, because an error response or
an unsigned list carries no signed tip. The `hash_without_policy` warning has no window
condition, because a server that does not prune has no reason to send a hash at any depth.

### How `canary check` reaches a state for one server and one block

Canary asks its Core node for the block hash at each height. Then, for each server:

1. **Record.** Fetch `/commitment/{hash}`. Check the signature against the pinned key, the
   `b` tag against the requested hash, and the `network` tag against Core. Then check `n`
   against the number of transactions Core counts in the block. BIP-352 gives at most one
   entry per transaction and none for the coinbase, so `n` must be below that number.
   Canary asks Core only when `n` is above zero. A record that fails these checks counts
   as no record. No record gives `unverified`. A request with no
   usable answer gives the reason `server_unreachable`. That covers no answer, `internal`,
   `not_ready`, an answer outside the API ([Errors](#errors)), and an answer longer than
   4096 bytes. The record's height is
   checked against Core only when the retention rule needs it.
2. **List.** Fetch `/tweaks/{hash}?dust_sat=0`. No list gives `unresolvable`, with the
   reason `list_not_served`. An error is no list, and so is an answer outside the API.
   So is an answer longer than `4 + 66n` bytes, the most a list of `n` positions takes.
   Canary reads no further, so a server cannot make it decode millions of positions.
3. **Receipt.** Check it as in [3. The receipt](#3-the-receipt). A missing or invalid
   receipt leaves the list unsigned and any finding unprovable.
4. **Decode.** Apply [the reader rules](#2-the-tweak-list). A list with a valid receipt
   that fails them gives `compromised`, reason `served_contradicts_record`, because the
   server signed those exact bytes. A list without one gives `unresolvable`, reason
   `list_unreadable`. A decoded length other than `n` gives `compromised`, reason
   `served_contradicts_record`, with or without a receipt. Any `hash` position from a
   server whose `/info` declared no pruning also raises a `hash_without_policy` warning.
5. **Window.** Apply [the retention rule](#4-the-retention-rule) to every absent position.
6. **Fill.** For every `hash` or `absent` position, look for the entry: another server's
   list for the same root, or an entry Canary computed from a payment you declared.
   Canary tries a declared payment's entry at each unfilled position and keeps the
   position where the root matches.
7. **Root.** Recompute the root once every position is full, a hash, or filled. Only
   after step 6.
8. **Cross-check.** Compare roots across servers for the same block hash.
9. **Declared payments.** For each payment you declared in this block, once step 7
   recomputed a root that matches the record:
   - No position holds the payment's entry or its hash. That gives `compromised`, reason
     `expected_payment_not_in_record`, with no spending check.
   - A position holds only the hash, or was absent outside the window and filled. If Core
     shows one of the payment's taproot outputs unspent, that gives `compromised`, reason
     `expected_payment_not_in_list`.

   A `compromised` result here replaces a `verified` or `resolved` result from step 7.

A `compromised` result from step 4 or 5 stands whatever steps 6 to 9 find. A list that
did not decode, or has the wrong length, stops at step 4, because its positions cannot be
matched to the record's. Otherwise Canary still fills and recomputes, because the recovered
entry names the transaction that was left out. When one server hits several reasons for
one block, the first in step order is the one recorded.

A block's state then comes from its servers' states, in this order of precedence:

1. `compromised` if any server is `compromised`.
2. Otherwise `disputed` if two servers signed different roots.
3. Otherwise `verified` if any server is `verified`, then `resolved` if any is `resolved`.
4. Otherwise `unresolvable` if any server is `unresolvable`.
5. Otherwise `unverified`.

The block's reason is the deciding server's reason, taking servers in `--indexer` order.
A verified block with two agreeing records always carries `records_agree`.

Warnings do not enter this precedence. A block can read Checked from one server while
another server holds a warning for it. The warning appears in `findings`, in
`canary status` and on the dashboard, so the other server's result does not bury the
refusal.

### `coverage[]`

Consecutive heights with the same state and the same reason merge into one range. Ranges
use heights, for display. Block detail uses hashes, because Canary compares blocks by
hash.

| Field | Type | Meaning |
|---|---|---|
| `from` | number | First height, inclusive |
| `to` | number | Last height, inclusive |
| `state` | string | One of the six codes |
| `reason` | string | One of the reason codes |

### `blocks[]`

| Field | Type | Meaning |
|---|---|---|
| `height`, `hash` | number, hex | The block, hash in display order |
| `state`, `reason` | strings | The block's state and reason |
| `servers` | array | One object per server, as below |

| Per-server field | Type | Meaning |
|---|---|---|
| `label` | string | Server label |
| `state`, `reason` | strings | This server's result for this block |
| `record_event_id` | hex or `null` | Id of the signed record |
| `n`, `root` | number, hex, or `null` | From the signed record |
| `positions` | object or `null` | Counts of `full`, `hash` and `absent` positions in the list |
| `filled` | number | Positions whose entry Canary recovered |
| `signed` | bool | Whether a valid receipt covered the list |
| `tip` | object or `null` | `height` and `hash` from the receipt |

### `findings[]`

A finding is a fact about a server and a block. There are three kinds:

- **`withheld`** names one server and comes from a `compromised` result. It is an
  accusation.
- **`disagree`** names two servers and comes from a `disputed` result. It says one of them
  lied, not which.
- **`warning`** names one server that did something an honest server would not, where
  nothing it signed shows it. It comes from `no_record_for_block`, from `list_not_served`
  or `list_unreadable` inside the window, or from `hash_without_policy`. It is not an
  accusation, and it does not change any block's state. A `hash_without_policy` warning is
  one per server and block, however many positions came as hashes. Its `position` and
  `txid` are `null`, and the block's `positions` counts show how many hashes there were.

| Field | Type | Meaning |
|---|---|---|
| `id` | string | 12 hex characters, stable across runs. See below |
| `kind` | string | `withheld`, `disagree` or `warning` |
| `reason` | string | For `withheld`, the `compromised` reason. For `disagree`, `records_differ`. For `warning`, the server's reason for that block, or `hash_without_policy` |
| `servers` | array | `label` and `pubkey` of each server named. One for `withheld` and `warning`, two for `disagree` |
| `block` | object | `height` and `hash` |
| `position` | number or `null` | The position in the list, when known |
| `txid` | hex or `null` | The left-out transaction in display order, when Canary knows it: it recovered the entry, or the entry belongs to a payment you declared |
| `evidence` | string or `null` | Evidence file name inside `evidence_dir`. `null` where v1 cannot write one: for `disagree` and `warning`, for `false_chain_claim`, `expected_payment_not_in_record` and `expected_payment_not_in_list`, for a list that fails the reader rules or has the wrong length, and when Canary did not recover the entry |
| `provable` | bool | True only when the evidence file carries a receipt and checks out |
| `first_seen` | time | The first run that saw it |
| `last_seen` | time | The latest run that saw it |

**Carrying findings forward.** `canary check` copies each finding from the previous state
file into the new one, so a later run does not clear it. When a run sees a finding whose
id is already present, it updates `last_seen`. It also updates `evidence` and `provable`
when this run wrote a file with a receipt where the old one had none. Every other field
keeps the value from the first run that saw it.

There is one exception. Before copying a finding, `canary check` asks Core for the
finding's block header. If Core has no header for that hash, the chain the finding was
about is gone, as when a regtest chain is wiped and mined again. The run drops that
finding and prints its id. A reorg does not drop a finding, because Core keeps the headers
of blocks that left its best chain. Evidence files stay on disk either way.

If the previous state file names a different network, `canary check` refuses to overwrite
it and exits with code 3. Use a separate `--state` path for each network.

**Finding id.** The id is the first 12 hex characters of the SHA-256 of this ASCII
string, with pubkeys sorted and joined by commas:

```
<kind>|<pubkeys>|<block hash, display order>|<subject>
```

The `<subject>` is the first of these that applies:

| Kind | Subject |
|---|---|
| `warning` | `reason:<reason>` |
| `withheld`, position known | `pos:<position>`, decimal |
| `withheld`, position unknown, transaction known | `txid:<txid>`, display order. This covers `expected_payment_not_in_record`, where the payment's entry sits at no position in the server's record |
| Otherwise | `-` |

Keying on the position keeps one id when a later run recovers an entry that an earlier run
could not. The position is fixed for a given block hash, because canonical order is.

For the example, `withheld|b1070620…270d|cafb64b3…09b8|pos:1` gives `827a8d3f502e`.

### `expected_payments[]`

The tripwire. A declared payment is a transaction the user made, so Canary can compute its
entry from Core and check each server's record and list for it
([Canary tripwire](2026-09-06-canary-design.md#5-canary-tripwire)). v1 checks the entry
only, not the output data a server serves for the payment. It asks Core whether the
payment's outputs are spent only to decide whether pruning can explain a missing entry.
In v1 the user makes and declares each payment by hand. Scheduled self-payments at random
times and amounts are planned for v2.

| Field | Type | Meaning |
|---|---|---|
| `txid` | hex | Display order |
| `block` | object or `null` | `height` and `hash` of the confirming block. `null` while unconfirmed |
| `outcome` | string | Overall outcome, below |
| `servers` | array | `label` and `outcome` for each server |

| Per-server outcome | Meaning |
|---|---|
| `found` | The server's list carries the entry in full |
| `withheld` | The server left the entry out of its signed record, or out of its list where pruning cannot explain it. It gets a `withheld` finding |
| `hash_only` | The server's record includes the entry, but its list does not carry it in full, and Core shows no taproot output of the payment unspent at or above the dust threshold. Legitimate pruning may explain it, so Canary does not accuse |
| `not_indexed_yet` | The server's tip is below the block |
| `unresolvable` | Canary could not check this server's list for the block |

The overall `outcome` is `not_eligible` when the transaction has no BIP-352 entry, and
`pending` while it is unconfirmed. Otherwise it is the first of these that any server
reached: `withheld`, `hash_only`, `unresolvable`. If none, it is `pending` while any server
reads `not_indexed_yet`, and `found` once every server has the entry.

### Writing rules

- `canary check` writes the file atomically. It writes `<path>.tmp` and renames it over
  `<path>`, so `canary ui` never reads half a file.
- If the existing file has a newer format, cannot be read, or names another network,
  `canary check` refuses to overwrite it and exits with code 3. Overwriting would lose
  findings.
- The file holds no secrets. Pubkeys are public.

### The update check: `/state.etag`

`canary ui` tells an open page when something changed, without reloading it. The page
polls `GET /state.etag` every 5 seconds while the tab is visible.

**ETag.** The value is the first 16 bytes, as 32 hex characters, of:

```
SHA-256( state file bytes ‖ 0x00 ‖ build id of the running canary ui, as UTF-8 )
```

A missing state file counts as zero bytes. The build id is part of the hash because a new
binary may render the same file differently, so the page must reload after an upgrade.

**Response.** `200`, `application/json`, `Cache-Control: no-store`, and an `ETag` header
with the same value in quotes.

| Field | Type | Meaning |
|---|---|---|
| `etag` | string | The value above |
| `build` | string | Build id of the running `canary ui` |
| `state` | string | `ok`, `missing`, `unreadable` or `newer_format` |
| `generated_at` | time or `null` | From the state file |
| `findings` | number | Length of `findings` |

```json
{ "etag": "50d858e0985ecc7f60418aaf0cc5ab58", "build": "0.1.0+abc1234", "state": "ok", "generated_at": "2026-10-03T08:32:11Z", "findings": 1 }
```

The `etag` in this example is illustrative, not the hash of the example file.

Each page embeds the `etag`, `build` and `findings` it was rendered from. On each poll it
compares, in this order:

| Change | Update bar says |
|---|---|
| `build` differs | Canary was updated. Reload |
| `findings` grew | New finding, with a `(1)` prefix on the tab title |
| `etag` differs | New results. Reload |
| The request fails | Can't reach Canary since HH:MM |

The page never contacts anything but the `canary ui` it came from.

## 9. The CLI

### Commands

| Command | What it does |
|---|---|
| `canary check` | Checks a height range against each server, writes the state file, and writes evidence files |
| `canary verify FILE [--json]` | Checks one evidence file offline and prints the result, or the VerifyReport with `--json` |
| `canary status [--json]` | Prints a summary of the state file, or the file itself with `--json` |
| `canary ui [--addr 127.0.0.1:7352]` | Serves the dashboard for the state file on a local address |

### `canary check` flags

| Flag | Required | Meaning |
|---|---|---|
| `--indexer URL=label` | Yes, repeatable | A server to check. Canary splits on the last `=`. Labels are unique, lowercase letters, digits and `-` |
| `--pubkey label=HEX` | Yes, one per server | Pins the server's 32-byte pubkey. `label=none` declares a server that signs nothing, so its blocks read Not checked. Canary never learns a key from `/info`, and refuses to start with exit code 2 if a server has no pin |
| `--core-rest URL` | Yes | Bitcoin Core REST base URL, for example `http://127.0.0.1:18443/rest`. Core must run with `-rest=1`. Canary uses it for height-to-hash mapping, the chain tip, the sync flag, the chain checks, each record's `n` and declared payments. A bare `--expect TXID` also needs `-txindex=1`, because without it Core's REST `/tx` searches only the mempool |
| `--from H`, `--to H` | No | Inclusive height range. Defaults: `0` and Core's tip |
| `--expect TXID[@BLOCKHASH]` | No, repeatable | A payment you made and expect each server to report. Both hashes in display order. With `@BLOCKHASH`, Canary reads the transaction from that block and needs no transaction index. It exits with code 2 if the transaction is not in that block. With a bare `TXID`, it asks Core's transaction index, and exits with code 5 if Core cannot find the transaction, naming both fixes |
| `--state PATH` | No | State file. Default `~/.canary/state.json` |
| `--evidence-dir DIR` | No | Where evidence files go. Default `~/.canary/evidence` |

`canary check` v1 accepts regtest and main. v1 is tested on regtest only, so on main it
prints a one-line notice saying so. It refuses any other chain with exit code 5, signet
included. Every signet reports the chain name `signet` to Bitcoin Core, and a custom
signet's network magic comes from its challenge. So the name cannot tell Canary which
magic to check records and receipts against. Signet needs a flag that names the network,
which is planned after v1. `canary verify` reads the magic from the evidence file
itself, so it names a signet file's network as [1. Conventions](#1-conventions) does.

```
canary check \
  --indexer http://127.0.0.1:8081=honest --pubkey honest=b3f217a31dbfb8ed4d37b47c28ba531a50bb64426ecf66496eaaeaf5a48b3724 \
  --indexer http://127.0.0.1:8082=withholder --pubkey withholder=b1070620799e7da6bbc296ec7ea6aacf7f027317af796abf35f0c9c83710270d \
  --core-rest http://127.0.0.1:18443/rest \
  --expect 01982d712503c4e22cd00be57b905bacf4d8bff0533c23c276c8b738da217c16@cafb64b3cfa7d9c38917ab7fd88107ba27342cadee3dcf2f85138a8322dc09b8
```

### `canary status`

Without `--json` it prints a status line, the counts and the findings, using the labels
from [8. The state file](#8-the-state-file):

```
Last check 2026-10-03 08:32 UTC · blocks 0–212 · regtest · canary 0.1.0 (abc1234)
212 Checked · 1 Data withheld
withholder left out an entry it had signed for: block 205, txid 01982d71…7c16.
  Evidence: omission-regtest-205-01982d71-b1070620.json. You can prove this to others.
```

Warnings print after the other findings, each on a line that starts `Warning:` and ends
`Not an accusation.` With `--json` it prints the state file's bytes unchanged, after
checking that the format is one it reads.

**The dashboard's status line.** `canary ui` shows the same line with two changes, both to
the time. It prints the time in the viewer's local time zone, where the terminal prints
UTC. And it follows the time with a relative age. For the run above, viewed in India six
minutes later:

```
Last check 2026-10-03 14:02 IST (6 min ago) · blocks 0–212 · regtest · canary 0.1.0 (abc1234)
```

Every other part is identical, and both lines come from the shared wording table. The
relative age is measured from `generated_at` when the page renders.

### `canary ui`

| Flag | Meaning |
|---|---|
| `--addr` | Listen address. Default `127.0.0.1:7352`. A non-loopback address exits with code 2 |
| `--state PATH` | State file to read. Same default as `canary check` |

It starts even when there is no state file yet, and then shows the "No check yet" page with
the command to run. It accepts only `localhost` and loopback `Host` headers and makes no
outside requests.

| Route | Shows |
|---|---|
| `/` | Overview |
| `/blocks` | Coverage ranges and the range table |
| `/blocks/{hash}` | One block's detail, display-order hash |
| `/findings/{id}` | One finding, by the id in [8. The state file](#8-the-state-file) |
| `/evidence/{name}` | Downloads an evidence file. It serves only names listed in `findings` |
| `/state.etag` | The update check |

### Exit codes

| Code | Meaning |
|---|---|
| 0 | Success. `check`: the run finished and saw no finding. `verify`: the file checks out. `status` and `ui`: normal |
| 1 | `check`: the run saw at least one finding of any kind, warnings included, new or seen again. `verify`: the file does not check out |
| 2 | Usage error: an unknown flag, a missing argument, a bad value, a server without a pin, a non-loopback `--addr`, or an `--expect` transaction that is not in the block named |
| 3 | Can't read the input. `verify`: the file. `status`: a missing, unreadable or newer-format state file. `check`: an existing state file it will not overwrite, because it is unreadable, has a newer format or names another network |
| 4 | `verify`: inclusion only, because the file has no receipt |
| 5 | Operational failure: Core unreachable, still in its initial sync or on a chain v1 does not accept, such as signet. Also an `--expect` transaction Core cannot find, a server that answers outside the API and proves nothing, because none of its records verifies and its `/info` is not `canary-info/1` ([Errors](#errors)), or a file or port that cannot be written or bound |

A Can't be checked or Not checked block does not change `check`'s exit code. Only
findings do.

## 10. What these formats do not cover

**Checked means the tweak list was checked. It never means payments were checked.**
Three limits follow from the formats above. The README and the demo's last act state them
too, and the design lists them under
[Limits of v1](2026-09-06-canary-design.md#limits-of-v1).

**Output-side withholding.** An entry is `(txid, tweak)` and nothing else. A wallet decides
whether a payment exists from output data that no format here commits to. On BlindBit v1
that is the new-UTXO filter and the `/utxos` list with its spent flag. On BlindBit v2 it is
each transaction's 8-byte output prefixes in `outputs_short`. A server can serve the
correct entry, then leave the output out of the filter, drop it from `/utxos`, mark it
spent, or drop its prefix. The wallet skips the payment without an error, and Canary marks
the block Checked. v2 plans to add each transaction's taproot output keys to its entry.
The receipt's `resource` byte exists so that a receipt for output data cannot pass as one
for a tweak list.

**Hash-only withholding under a pruning policy.** A server that declares `prunes_spent`
may serve an entry as its 32-byte hash. The hash satisfies the retention rule and the root
recomputes, so the block reads Checked, gap filled, with the reason `hash_retained`.
Telling legitimate pruning from hiding needs to know whether the transaction's taproot
outputs are spent, and nothing in these formats says. v1 policies are also unsigned. They
come from `/info`, and `policy_ref` is all zeros. So when a server that declares no pruning
sends a hash, v1 raises a `hash_without_policy` warning, never an accusation. The warning
catches only a server that did not declare pruning. Declaring it costs a hiding server
nothing, because nothing signs the declaration. A declared payment catches this variant
only for a payment you made yourself, through `expected_payment_not_in_list`. That finding
is not provable to others, because the evidence format has no way to show an output
unspent.

**Regtest only.** v1 is built and tested on regtest only, against its own reference
indexer. `canary check` accepts regtest and main, and refuses signet until a flag can name
the network ([9. The CLI](#9-the-cli)). No deployed server speaks this API, signs these
records or sends these receipts.
Nothing has been shown on signet or mainnet, or with a wallet in the path, because v1 has
no proxy and `canary check` only reports. In the demo one Core node feeds both the indexer and Canary.
And the reference indexer and Canary share the `canonical` package, so when their results
match, that tests the protocol, not two independent implementations.

**Smaller gaps, also open in v1:**

- **A server that declines to answer is warned about, not accused.** v1 accuses only a
  server that served a list its own record contradicts. A server that signs records for
  the blocks on both sides of the victim's block but not that block gets a warning with
  the reason `no_record_for_block`. So does a server that signs a record and then refuses
  the list, or sends an unsigned list that fails the reader rules, inside the window. The
  warning names the server but proves nothing, because nothing it signed shows the
  refusal.
- **A server that signs records only from some height upward** gets no warning for the
  blocks below its first record. It looks the same as a server that started indexing
  later.
- **A server that proves nothing can still stop the run.** When none of a server's
  records verifies under its pin and its `/info` gives no usable answer, Canary can't
  tell a hostile server from a wrong `--indexer` URL. One answer outside the API from it
  then stops the run with exit code 5, and nothing is saved, including other servers'
  results. None of its records verified, so no finding in that run could name it. It can
  still deny you the run, for example to cover another server. Leave it out of
  `--indexer` and run again.
- **A record that claims more entries than its block can hold is not accused.** It
  counts as no record, so between two valid records it raises the `no_record_for_block`
  warning, and elsewhere nothing. Its `n` is a signed claim the user's node contradicts.
  But v1 has no reason code for it, and the check exists to bound what one record costs
  the run. Canary checks `n` only against the transaction count, so a record that claims
  fewer entries than that, real or not, is still judged by its list.
- **A record longer than 4096 bytes is not read.** It reads Not checked, reason
  `server_unreachable`, like no answer, and raises no warning. Its signature may verify,
  but Canary does not read that far. A v1 server never signs a record that long.
- **A list longer than its record allows is not read.** An answer over `4 + 66n` bytes
  reads Can't be checked, reason `list_not_served`, with the warning inside the window.
  Under a valid receipt it would be a signed contradiction, but Canary does not read that
  far. A list of the wrong length that fits in those bytes is still accused, with the
  reason `served_contradicts_record`.
- **A slow server can stretch the run.** Each request may take up to 30 seconds. Canary
  stops asking a server only after 3 requests in a row get no answer, and a slow answer
  is an answer. So a server that answers each record and list just inside the limit adds
  about a minute per block, about three hours for 200 blocks. An interrupted run saves
  nothing. The way out is to leave that server out of `--indexer` and run again.
- **A refused record raises no warning.** A record request can get no answer, `internal`,
  or an answer outside the API. Each reads Not checked with the reason
  `server_unreachable`. An `unknown_block` answer between two signed records raises the
  `no_record_for_block` warning instead. So a withholder that refuses the record rather
  than the list leaves no warning behind.
- **A false chain claim is accused but not provable.** A gap excused by a signed height
  or tip that Core contradicts gives a `withheld` finding with the reason
  `false_chain_claim`. Checking it needs a node, and `canary-evidence/1` has no claim for
  it, so the finding records `"provable": false`.
- **A record that leaves out a declared payment is accused but not provable.** The
  reason is `expected_payment_not_in_record`. You know the record is incomplete because
  your own Core shows the transaction in that block. A stranger would need the block to
  check that, and `canary-evidence/1` has no claim for it, so the finding records
  `"provable": false`. When the record includes the entry and only the list leaves it out
  inside the window, the finding is an ordinary `absent_in_window` omission with an
  evidence file. That file's `context` records `found_by: expected_payment` when the
  declared payment supplied the entry.
- **An unconfirmed tip can shorten the window by up to 6 blocks.** A signed tip within 6
  blocks of Core's tip that Core cannot confirm gives Can't be checked, reason
  `tip_unconfirmed`, and no finding. This works only for a block already at least 138
  blocks below Core's tip. That block leaves the window within 6 more blocks, so a
  withholder can use the trick on the window's last 6 blocks and nowhere else
  ([4. The retention rule](#4-the-retention-rule)).
- **Some signed contradictions have no evidence file.** A list with a valid receipt whose
  length differs from `n`, or that fails the reader rules, is accused. The receipt signs
  those bytes, so the contradiction is provable in principle. But `canary-evidence/1`
  carries the `omission` claim only, so v1 records `"provable": false`.
- One server alone cannot show that its record is complete. Its blocks read Checked with
  the reason `own_record`, and only a second server or a declared payment tests the record.
- `disagree` findings have no evidence file. `canary-evidence/1` carries the `omission`
  claim only.
- Records travel over HTTP from each server in v1. Publishing them to relays, which the
  second condition of the security claim relies on, is not part of these formats.
